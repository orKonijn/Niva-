## Maintenance runbook (prepared locally; not activated on hosted Site)

For these repairs the appended Node migrations extend through `005` and D1 migrations through `0003_late_sentinel.sql` (constant-default erasure marker). Version 17 deployment completed successfully with the appended schema migration; no destructive data operation was performed. Apply the pending migrations before serving repaired APIs in any separate environment. Existing migrations are unchanged. Lifecycle initialization deterministically picks at most one valid confirmed legacy active resume and preserves content. Keep a pre-migration backup and prove restoration on disposable staging data.

Run a trusted platform scheduled trigger at least every five minutes against the exported Worker `scheduled` handler, or call `POST /api/ingestion/run` with the server-only `NIVA_INGEST_SECRET` bearer secret (minimum 32 characters). `POST /api/maintenance/run` performs cleanup alone with the same authentication. Do not put secrets in client code, URLs or logs. HTTP invocations record `manual`, not a falsely claimed native scheduled execution. If using external HTTP scheduling, observe its delivery logs plus maintenance timestamps separately.

The retention target is physical removal within 60 minutes after expiry. Reads deny expiry immediately. Each maintenance invocation runs cleanup before contacting any provider; outages cannot skip cleanup. Overdue `cleanupOverdue` or `schedulerOverdue`, ingestion `SOURCE_FAILURE`, and retention `CLEANUP_FAILED` require operator action. The authenticated `/api/career/operations` exposes timestamps, last errors, removed count and lag; the resume page explains overdue cleanup. No external alert delivery is configured. Node logs failures; wire an operator alert on staging, then observe two due cycles and a source outage. Native Worker scheduling is prepared but no cron is added to hosting configuration by this pass.

## Reviewed-source handoff and artifact verification

1. Review and commit local source. `node scripts/prepare-reviewed-source.mjs NEW_DIRECTORY` refuses dirty source and existing destinations, copies only tracked files (no ignored secrets/databases), and writes `.openai/reviewed-source.json` with the GitHub commit, exact file set and digest. It performs no network or Git mutation.
2. A future authorized Sites source import can have its own Git lineage. Build validates both the manifest file set and bytes; changed content refuses the mapped-source claim. Build metadata includes that reviewed GitHub SHA and current Sites checkout SHA. Preserve bytes/newline policy when importing; a normalization mismatch must be reviewed, never bypassed.
3. `/build-info.json` records source SHA/tree, content digest, static-client artifact digest, UTC build time and dirty state. Static digest excludes metadata itself, server and `.openai` to avoid self-reference. Record Worker bundle SHA256 separately in release evidence. Metadata is traceability, not signed attestation.
4. After a separately authorized deployment, compare retrieved metadata and static bytes with the reviewed build and record Site saved version, source commit and schedule observations. The repaired version 16 was subsequently deployed and its live build metadata and schema were checked; actual recurring scheduling, independent-user isolation and restoration remain unverified.

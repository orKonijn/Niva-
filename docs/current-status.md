## Maintenance runbook (prepared locally; not activated on hosted Site)

For these repairs the appended Node migrations extend through `005` and D1 migrations through additive auth migration `0004_ambitious_psylocke.sql` (the preceding `0003` retains its erasure marker). Version 17 deployment completed successfully with the appended schema migration; no destructive data operation was performed. Apply the pending migrations before serving repaired APIs in any separate environment. Existing migrations are unchanged. Lifecycle initialization deterministically picks at most one valid confirmed legacy active resume and preserves content. Keep a pre-migration backup and prove restoration on disposable staging data.

Run a trusted platform scheduled trigger at least every five minutes against the exported Worker `scheduled` handler, or call `POST /api/ingestion/run` with the server-only `NIVA_INGEST_SECRET` bearer secret (minimum 32 characters). `POST /api/maintenance/run` performs cleanup alone with the same authentication. Do not put secrets in client code, URLs or logs. HTTP invocations record `manual`, not a falsely claimed native scheduled execution. If using external HTTP scheduling, observe its delivery logs plus maintenance timestamps separately.

The retention target is physical removal within 60 minutes after expiry. Reads deny expiry immediately. Each maintenance invocation runs cleanup before contacting any provider; outages cannot skip cleanup. Overdue `cleanupOverdue` or `schedulerOverdue`, ingestion `SOURCE_FAILURE`, and retention `CLEANUP_FAILED` require operator action. The authenticated `/api/career/operations` exposes timestamps, last errors, removed count and lag; the resume page explains overdue cleanup. No external alert delivery is configured. Node logs failures; wire an operator alert on staging, then observe two due cycles and a source outage. Native Worker scheduling is prepared but no cron is added to hosting configuration by this pass.

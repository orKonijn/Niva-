## Separate ingestion, cleanup and independent alerting

The latest recorded version18 publication retained the existing inactive hosted schedule. This pass does not activate one. After separate approval:

- Store `NIVA_INGEST_SECRET` as a server-only runtime secret with at least32 characters. Trusted external writer requests must satisfy both the hosting service gate and this bearer check. For Sites, the supported unattended credential is sent only to that Site as `OAI-Sites-Authorization: Bearer <service-token>`; dispatch consumes it. The endpoint separately requires `Authorization: Bearer <NIVA_INGEST_SECRET>`. These are different headers and permissions; no token is generated or activated here. A service credential alone is not a signed-in user. Never place secrets in URLs, source, screenshots, output or automation prompts.
- Configure a trusted ingestion job every five minutes, calling `POST /api/ingestion/run` with bearer authentication and JSON body `{}`. Provider leases still limit actual source checks to their 10/15-minute cadence. Native Worker `scheduled` uses the same runner. HTTP jobs remain labelled manual in server evidence; use scheduler delivery records to establish their unattended nature.
- Configure a **separate cleanup-only job** every five minutes, calling `POST /api/maintenance/run`. Cleanup runs before source retrieval in combined runs, but a separately delivered job also survives a hung ingestion task. Immediate read denial is independent of physical cleanup. The target remains physical deletion within60 minutes after expiry; verify actual timestamps/counts rather than asserting an SLA from code.
- Run the watchdog from independent infrastructure every five minutes, outside the application timer/scheduler failure domain. Configure `NIVA_HEALTH_URL=https://STAGING_HOST/api/maintenance/health`, the server secret, optional private-Sites `NIVA_SITES_SERVICE_TOKEN`, approved `NIVA_OPERATOR_ID`, approved HTTPS `NIVA_ALERT_URL`, optional `NIVA_ALERT_SECRET`, and a private durable `NIVA_WATCHDOG_STATE` path. Inspect `npx tsx scripts/maintenance-watchdog.mts --plan` first; only explicitly approved `--run` sends an alert. The health endpoint is bearer-protected and returns operational metadata only. Do not re-use visitor cookies for unattended work.
- Watchdog uses a20-minute ingestion-run heartbeat bound (plus up to five minutes to its next check) and a60-minute cleanup bound. A recent manual/external run is distinct from evidence of a native scheduled trigger; `scheduledObserved` retains that distinction, while fresh external ingestion can be healthy. Source failures are separately alerted. A heartbeat does not prove the actual scheduler or source cycles. Watchdog sends only service name, operator alias, reason codes and observation time. It alerts on missed scheduler/cleanup, recorded failures and unreachable health. Successful same-reason deliveries are limited to once/hour; failures do not acknowledge delivery and retry on the next five-minute invocation. State loss can duplicate a notification. Wire watchdog process failure/exit1 to infrastructure monitoring; no program can alert while its own host is entirely offline without an independent monitor.
- Observe two successive due source cycles (allow more than30 minutes to cover both cadences), remove a synthetic upstream listing and verify closure, then cause provider outages and verify truthful stale preservation plus cleanup within the bound. Stop the application job and confirm the named operator receives/acknowledges a real watchdog alert. A local loopback receiver test proves local transport only; it is not production delivery.

## Performance and rollout limits

The bounded metadata pass reads128 rows at a time and retains only selected card IDs; public cache reindex uses24-row compare-and-swap batches. A synthetic5000-record local SQLite/Node benchmark reduced sampled heap145.7MB to36.1MB and serialized database return data34.6MB to13.7MB; observed latency523ms to428ms. This comparison is the new rich-evidence implementation before/after bounding, **not proof of an old production memory failure**. Heap sampling is not peak memory; added D1 round trips require staging measurement. See [benchmark](verification/audit40-benchmark.json), [comparison](verification/audit40-benchmark-before.json), `scripts/audit40-benchmark.ts`.

No DDL migration is required; new fields use backward-compatible public/account JSON. Existing accounts default to unknown citizenship and non-exclusive rights. Candidates must explicitly confirm new fields before they can create conflicts. Old public caches are reindexed before filters. Old Veeva rows lack provider-only workplace metadata, and flattened cached descriptions cannot reconstruct old section breaks: allow the next normal due ATS ingestion before acceptance in staging. No extra provider quota, activation or manual production refresh was used.
